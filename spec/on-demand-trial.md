# NightShift 按需求交付試用版本

Date: 2026-10-24
Status: design confirmed; ticket breakdown proposed

本規格記錄已確認的設計與實作工單，並整合到 docs 的主規格。文件狀態不代表各項驗收已通過；工單檔案本身不會排入 queue 或發布 GitHub issue。

## 問題與目標

NightShift 的 worktree 隔離很少被使用，卻讓專案開發持續負擔分支同步、更新、工作目錄與發布流程的維護成本。移除這項功能，Worker 直接在專案目錄執行任務。

使用者仍需要在開發期間試用成果。使用者向 Planner 提出試用需求後，Planner 插入一張普通 task，讓 Worker 建置並取出當下可跑的版本。主要交付物通常是一份 bin；如有必要的 script 或其他資源，由該 task 一併檢查，並在交付時說明。

## 已確認的行為

### 1. 直接在專案目錄開發

- 移除 NightShift 自動建立、重用與同步 Worker worktree 的功能，以及成功 task 後自動發布 preview 的流程。
- Worker 的任務執行、驗證、提交、失敗保存與復原，都使用目前專案目錄；既有的任務與嘗試復原契約仍須成立。
- 不保留啟用 worktree 的執行模式。既有隔離設定須有明確的退場處理，不能讓升級後的部署繼續進入舊流程。
- `.worker.env` 不再是設定來源。runtime 預設值在 launcher，啟動環境可覆寫；agent 設定集中在 name-keyed registry。舊 env 僅保留供人工遷移，不讀取或恢復其設定作用。
- 移除功能不代表刪除既有 worktree、分支或 preview 資料。升級須保留尚未整合的工作，並提供人工檢查與遷移說明。
- 本功能不提供多個 Worker 同時修改同一份專案內容的排程或衝突處理。

### 2. 由 Planner 插入試用 task

- 使用者提出試用需求後，由 Planner 建立普通 task，遵循現有 queue、執行、audit、提交與驗收機制。
- 試用 task 排在目前執行中的 task 完成之後、其他尚未開始的待辦之前；若 Worker 閒置，則排在待辦首位。
- 插入必須使用既有 queue 鎖定與替換機制，保留其他待辦的相對順序，不遺失、重複或重新執行已被 claim 的 task。
- runtime 不新增試用專用 task 類型、發布排程器或每張 task 完成後的自動發布程序。
- 工單需描述目標程式、建置及最低限度的可執行檢查、交付位置、必要資源、衝突檢查與交付證據。具體建置方式由 Planner 依目標專案安排。
- 擷取的是試用 task 執行時、前一張 task 完成後的版本；不是使用者提出要求當下尚在變動的半成品。

### 3. 交付當下可跑的 bin

- 依專案的建置方式產出 bin，完成與專案相符的最低限度可執行檢查；不能只以編譯成功宣稱可以試用。
- 將 bin 放在不會被後續一般開發或建置直接覆寫的位置，交付可定位的版本。不要依賴對開發中輸出檔案的 symlink 作為獨立 bin。
- 預設以 bin 為主要交付物；如需 script、設定或其他資源，交付說明必須列出所需項目、位置與使用條件。可合理隨附的資源可一併交付；需要共用的資源依下節處理。
- 每次交付記錄來源 task、可追溯的程式版本、建置／檢查結果、產物位置及實際啟動方式。產物工作不要求為了完成 task 而製造無意義的原始碼變更或提交。
- 建置或最低限度可執行檢查失敗時，回報原因，由 Planner 安排修復；不將失敗產物標示為可跑版本，也不以舊版冒充本次成果。
- 成功交付後，Worker 可接續執行 queue；新的試用交付不覆蓋上一份已交付的 bin。

### 4. 在同一張工單檢查資源衝突

- 試用 task 檢查 bin 需要的 script、其他資源，以及試用與後續開發可能共用的內容。例如：仍從專案目錄讀取的 script／資源、建置會覆寫的檔案、設定、資料庫、裝置或連接埠。
- 交付時說明檢查範圍、發現的共用依賴與衝突，不能在沒有足夠證據時宣稱試用完全獨立。無法確認的必要依賴也須說明。
- 有資源衝突時，交付內容包含原因、建議暫停 Worker，以及適用於該部署的具體暫停指令。Worker 將證據交回 Planner，由 Planner 向使用者提示。
- 是否暫停由使用者決定。試用 task 不因發現衝突就自行建立暫停旗標；Worker 完成該 task 後照常接下一張。
- 暫停指令必須使用實際部署的 pause 設定與正確路徑。既有 pause 機制是在 task 邊界阻止後續派工，不會立即終止正在執行的 task；提示須說明如何確認 Worker 已停止派工，以及何時適合啟動試用。
- pause 設定從實際 Worker 啟動環境與 launcher 預設值解析，不能讀取已退場的 worker env 檔。status／watcher helper 不會載入 launcher，須傳入相符的自訂路徑與 Worker ID，避免查到另一份狀態。
- 資源衝突提示不取代可執行檢查；若目前無法安全完成該檢查，須明確回報尚未驗證的條件，交由 Planner 處理，不虛報成功。

## 與現有規格的關係

這是目標行為；目前實作觀察與限制由主規格及來源覆蓋索引記錄。操作與部署文件須一致反映移除 worktree／自動 preview 及 worker env 設定來源的契約，實際完成度仍以驗收證據為準。

本規格只移除 Worker 開發隔離及自動 preview 發布。失敗嘗試的保存、baseline 快照與復原是任務可靠性機制，仍須保留；不能因名稱也含 snapshot 就一併移除。

既有 AI Agent Adapter Protocol 的工作目錄、audit、復原與合法無原始碼變更結果，均適用於試用 task。其實作工單中若仍要求驗證 isolation／自動 preview，整合時須依本規格調整成專案目錄執行與按需求試用的驗收。

## 工單與驗收

工單拆解見 [Implementation tickets](on-demand-trial-tickets/README.md)。每張工單各自包含可交付行為、blocking edges 與驗收條件。工單粒度與依賴待審閱；文件編號不代表已經派工。

完成後應能演示：Worker 直接開發 → 人要求試用 → Planner 插入 task → 交付可跑 bin 與資源檢查結果 → Worker 繼續開發 → 人遇到提示的衝突時自行暫停並確認狀態後試用。
