# Automatic hot/cold acceptance and Planner-directed recovery

Publication status: local draft; GitHub CLI is not authenticated. Publish to the project GitHub issue tracker with the `ready-for-agent` label once authentication is available. No runtime implementation is included in this document.

## Problem Statement

NightShift currently mixes Worker verification, runtime verification before and after commit, confidence-based Planner acceptance, manual score resolution, and report handling. A passing mechanical audit can print a fixed test-count claim without proving that a task's new TDD case was included in the executed suite. Tests mentioned only in a ticket can disappear from verification after that task ends.

The user wants unattended successful execution: scripts own verification, commits and scoring; Planner chooses work using scores and intervenes on failures. Failures must stop ordinary dispatch and preserve diagnostic evidence long enough for Planner to inspect, then subsequent tasks start from a clean working directory. Project owners determine which tests run rather than accepting NightShift's hard-coded testing policies.

## Solution

Use one script-owned acceptance flow on the project's current branch. Worker implements its task, permanently integrates its TDD cases into project hot tests, and hands off a commit message and structured test declarations. The runtime may stage the task changes, runs hot plus task-specified cases and retained mechanical protections, and commits and scores automatically only after all requirements pass.

Ghost can complete delivery metadata, connect existing tests to hot, run verification and produce reports. Ghost cannot repair product code or alter tests to make failures pass. If it cannot complete the handoff successfully, the runtime pauses ordinary dispatch and notifies Planner. Planner uses scheduling operations to prioritize new issue tasks, revise instructions and explicitly restart execution. Failed work is not resumed or backed up; the next Worker starts clean.

After a user-configured number of successful development-task commits, the runtime inserts an independent cold task into the FIFO. Cold runs serially as a script-owned task. Success produces no user notification, Worker score change or Git record; failure produces a new issue and the same diagnostic/pause workflow, without retracting earlier scores.

## User Stories

1. As a project owner, I want Planner and Worker to use the project's current branch, so that accepted changes do not require a separate branch or merge procedure.
2. As a project owner, I want project-defined hot and cold commands, so that my project's test frameworks and cases determine acceptance.
3. As a Worker, I want one handoff containing a commit message and TDD declarations, so that the runtime can complete delivery after I exit.
4. As a project owner, I want task-specified cases included in hot acceptance, so that a passing general suite cannot omit a ticket's required checks.
5. As a project owner, I want new TDD cases permanently discoverable through hot, so that they continue protecting later tasks.
6. As a project owner, I want the runtime to reject missing TDD declarations, so that a Worker cannot silently claim testing happened.
7. As a project owner, I want declarations checked against actual test changes, so that naming an unchanged existing case is insufficient.
8. As a project owner, I want runtime-produced discovery and execution evidence, so that a declaration cannot substitute for running a test.
9. As a project owner, I want skipped, deselected or undiscovered required cases rejected, so that a successful process exit cannot hide missing coverage.
10. As a Worker, I want to run red/green TDD during implementation, so that runtime acceptance does not replace the development loop.
11. As a project owner, I want scripts to commit and record success automatically, so that successful tasks do not wait for Planner acceptance.
12. As a Planner, I want scripts to maintain existing Worker scoring rules, so that I can assign work using current scores.
13. As a project owner, I want confidence and retry-based acceptance tiers removed, so that every development task follows the same deterministic gate.
14. As a project owner, I want Ghost to supply missing delivery details or hot wiring, so that simple handoff omissions do not immediately require Planner intervention.
15. As a project owner, I want Ghost prohibited from changing product code or test assertions, so that diagnostics cannot disguise a failed implementation.
16. As a Planner, I want failed commands, outputs, task identity and version information in a report, so that I can decide how to replan.
17. As a Planner, I want notification even when Ghost fails or times out, so that diagnostic failure cannot silently stall supervision.
18. As a project owner, I want ordinary dispatch paused after unresolved verification failure, so that further tasks do not accumulate on a known failure.
19. As a Planner, I want to insert issue tasks as near the front of the FIFO as possible, so that recovery uses normal scheduling.
20. As a Planner, I want to revise task prompts and explicitly restart execution, so that a script cannot resume ordinary work before I finish replanning.
21. As a Worker, I want every new task to begin with a clean tracked and nonignored working tree, so that it does not inherit failed implementation work.
22. As a project owner, I want ignored files retained during cleanup, so that dependencies, local configuration and diagnostic artifacts survive.
23. As a project owner, I want cold scheduled after N successful development commits, so that broader regression testing has a configurable cadence.
24. As a project owner, I want cold to execute as an independent script task, so that it does not require a Worker or concurrent worktree.
25. As a project owner, I want successful cold runs to remain silent and Git-clean, so that periodic checking does not create noise or commits.
26. As a Planner, I want cold failures treated as new issues without reversing prior scores, so that diagnosis does not require historical blame accounting.
27. As a project owner, I want durable internal progress state, so that restart does not duplicate a commit, score, cold insertion or notification.
28. As a maintainer, I want documented hot/cold migration instructions, so that existing Worker and Ghost task-case verification can move to the common gate.

## Implementation Decisions

- **Ownership and branch model.** Worker implements; runtime accepts, commits and scores; Planner supervises scheduling and recovery. Execute in the project directory on its current branch. Remove active mechanisms that separate Planner and Worker development branches; do not delete historical branches or worktrees merely to implement this feature. There is no acceptance-time merge or push.
- **One handoff and acceptance gate.** Extend the structured Worker-result contract with explicit TDD declarations and the existing commit message. Worker exits before runtime takes over. Runtime can stage allowed task paths before verification, but no commit or success score is allowed until hot, evidence checks and retained mechanical protections pass. Remove duplicate script-owned post-commit execution of the same task VERIFY; Worker may still run tests for TDD.
- **Project-defined entry points.** Project configuration supplies hot, cold and the cold interval. Hot executes both the project's persistent suite and task-specified required cases. Missing hot configuration is a recoverable handoff problem for Ghost, never a silent successful no-op. Do not invent commands or messages to bypass the gate.
- **TDD declaration contract.** For development tasks, require a nonempty structured list of added or substantively updated TDD cases, with stable project/framework case IDs and corresponding test source files. Missing or empty declaration fails acceptance. An unchanged case listed without an associated test change fails acceptance. A generic no-change outcome must not bypass these requirements while delivering product changes.
- **Check actual test changes.** Compare declared test sources with the task-start baseline, not merely the staged-file list or Worker prose. Require actual added or modified test content associated with the declared cases. Changes only to a declaration, report, comment or hot registration cannot stand in for changed TDD test content. Test adapters must expose enough source/case information to validate this association; unsupported or ambiguous evidence must fail explicitly rather than assume success.
- **Prove permanent hot membership.** A project-owned test adapter exposes normal hot discovery and machine-readable case execution results. The runtime invokes it and records evidence itself. Each declared TDD case must be discoverable through the persistent hot entry point with the task-specific case list absent. Running a case only through a temporary ticket command is insufficient. Discovery/registration definitions and test sources necessary for continued hot inclusion must be delivered with the task rather than left only in runtime metadata or ignored files. Existing framework auto-discovery can satisfy this without a per-case manual registry.
- **Prove execution.** Every declared TDD case and every task-required case must actually execute and pass in the current script-owned hot run. Discovery alone, a successful command exit, Worker claims, skipped/deselected cases, stale results or a fixed `Tests_Run` label are insufficient. Evidence binds task/attempt, invoked commands and case IDs to this run. Validate all configured hot commands' exit statuses as well as required-case results. Projects supply framework-specific discovery/result adapters; NightShift does not infer case execution by searching human-readable output for test-count strings.
- **Limits of mechanical evidence.** Source changes, discovery and execution establish traceable integration; they cannot prove that an assertion meaningfully specifies the requested behavior. Do not claim semantic TDD quality from a manifest or file hash. No new general assertion-count or deletion-count policy is introduced. Baseline comparison serves test-change validation, not an additional concurrent-edit revalidation loop.
- **Mechanical protections.** Retain task-scope restrictions and staging/commit isolation so unrelated changes cannot be accidentally included. Remove hard-coded assertion nondecrease, deletion limits, framework-specific full-test commands, generic zero-test heuristics, confidence tiers, retry-based manual checks and Planner acceptance waits. Project hooks and explicit case evidence replace testing policy. Starting dirty work is cleaned before Worker dispatch as specifically authorized; this is separate from refusing to mix unrelated changes into an active task's commit.
- **Ghost scope.** Ghost may add missing commit metadata, connect already-written cases to hot, execute the common verification entry point and write a diagnostic report. Hot wiring/configuration edits are permitted only for that purpose; product source, test assertions and test behavior cannot be changed, tests cannot be removed or weakened, and unrelated script changes are prohibited. Runtime checks this boundary. A valid Ghost handoff returns to the same script-owned gate; Ghost does not commit independently. Product-test failures lead to diagnosis and Planner recovery, not Ghost implementation repair. Bound Ghost execution; failure, timeout or invalid output still delivers available evidence to Planner.
- **Failure lifecycle.** Prevent ordinary dispatch while an unresolved failure is being diagnosed. Preserve the dirty/staged scene for Ghost and Planner inspection until the next explicitly restarted dispatch. Reports include task/attempt, hot or cold stage, actual command/exit/output, case evidence, available commit/base identity and Ghost status. Reports live outside the subsequent cleanup scope. Unresolved gate, mechanical, commit or handoff failures cannot receive a success score or ordinary continuation.
- **Cleanup.** Before the next Worker starts, restore tracked index/worktree changes to the current baseline and delete nonignored untracked files, including failed test additions; verify clean status. Keep ignored files and diagnostic reports. Do not stash, archive patches, back up failed changes or apply them to a subsequent task. Cleanup failure leaves dispatch paused. This spec authorizes the target runtime behavior; creating this spec does not clean the current repository.
- **Planner recovery.** Planner reads evidence and scores, revises prompts and reprioritizes the FIFO through the scheduling script, putting issue tasks as early as possible. Planner explicitly restarts the whole flow. Repair is an ordinary new task with the same hot and failure behavior; no special repair queue, mandatory failure-specific cold gate or script-controlled automatic resume is introduced. Planner ordinarily delegates implementation, except at the lowest task level.
- **Scoring.** Keep existing scoring arithmetic and update it automatically and idempotently. Hot success plus successful commit records task success; a failed hot task records failure through the existing rules. Remove manual accept/reject resolution as a success prerequisite. A later cold failure is a separate issue and never retracts prior successes or assigns historical blame penalties. Cold does not count as Worker work or alter Worker score. Internal durable records remain for restart correctness; routine successful report archival is removed.
- **Cold scheduling.** Count successful committed development tasks only. After configurable N completions, atomically insert one script-owned cold task in the FIFO using the existing queue insertion seam. Cold itself, failed tasks, research tasks and tasks without development commits do not advance the counter. Run serially in the project directory, without background Worker execution or an added test worktree. Check the execution-time HEAD against the last successfully cold-tested commit; skip an already-passing unchanged commit. Coalesce duplicate pending cold requests. Maintain cadence and last-passing-commit state across restarts, with a completed/covered interval reset so an unchanged successful version cannot create an insertion loop.
- **Cold outcome.** Run the configured cold command on the execution-time revision. Success is silent: no user-facing report or notification, Worker score, commit, branch operation or versioned-file change; update only ignored/internal scheduling state. Cold hooks must keep their outputs out of tracked/nonignored product files; unexpected product changes cannot be silently committed or reported as a clean success. Failure generates diagnostic evidence through Ghost, pauses dispatch and alerts Planner as a new issue. Missing/invalid cold configuration when a configured cold task is due is an explicit failure, not a silently successful command.
- **Documentation and migration.** Document configuring hot/cold and N, mapping existing task VERIFY into hot, permanent TDD discovery, case declaration and machine-readable execution evidence, commit-message handoff, Ghost's permitted hot wiring, failure cleanup and explicit restart. Migrate Worker and Ghost instructions and all existing script-owned task-case execution to the common hot flow. Explain that successful cold has no Git record and that internal runtime records remain. Update obsolete manual Planner-acceptance language and glossary references, preserving the term Planner acceptance rollback only where historical behavior is actually discussed.

## Testing Decisions

- Prefer the existing public runtime CLI/task lifecycle seam with a fake adapter, temporary Git repository and deterministic project hot/cold hooks. Observe command execution, working tree, HEAD, queue order, score, pause state and notifications. Existing public Worker verification-evidence tests and runtime lifecycle/queue tests provide prior art. Test external behavior rather than private helper calls or exact prompt text.
- Use the project discovery/result contract as a replaceable external test hook at that same lifecycle seam. Avoid adding separate independently mocked seams for each internal verification stage. Confirm the proposed seam with the user; it was presented during spec preparation and no alternative was supplied at draft creation.
- Demonstrate successful Worker handoff causes one script-owned hot acceptance, a scoped commit and one score update with no Planner acceptance; restart/replay cannot duplicate commit or score. Assert Planner and Worker remain on the same original branch.
- Demonstrate added TDD remains discoverable and executed on a subsequent unrelated task with the original task metadata absent. Include framework auto-discovery and explicit hot registration fixtures.
- Reject each distinct TDD omission: missing declaration; empty declaration; unchanged declared tests; metadata-only edits; source changed but declared case not found; case running only via task-specific arguments; discovered but skipped/deselected case; stale execution evidence; a required case missing from results; failed case despite a zero exit; and failed command despite passing case records. No commit or success score is produced.
- Cover Ghost supplementing a missing message and hot wiring for existing tests; both must return through the common gate. Ghost source/test mutation, timeout, invalid output or persistent failure must leave dispatch paused and send available evidence to Planner.
- Cover stage-before-hot behavior: failure creates no commit, leaves the scene available for diagnosis, and later explicitly restarted dispatch cleans tracked/staged/nonignored untracked files before launching a new Worker. Verify ignored artifacts and reports survive, no failed patch is stashed/reapplied, and cleanup failure blocks launch. Retain scoped-commit protection tests.
- Cover configured N counting only successful development commits, independent cold task insertion and serial execution, execution-time commit checks, unchanged-commit skipping, interval reset, pending-request deduplication and restart recovery.
- Assert successful cold has no Worker invocation, user notification, Worker score change or Git change. Assert cold failure creates diagnostic evidence and pauses without changing historical scores. Verify dirty cold outputs cannot silently pass as a Git-clean success.
- Cover Planner scheduling an issue before ordinary pending tasks, changing instructions and explicitly restarting. Failed repair tasks repeat ordinary failure handling; no hidden repair-specific acceptance or automatic resume occurs.
- Validate migration with representative configured projects rather than hard-coding a single framework in runtime. Include missing hook/result-adapter configuration and externally visible diagnostic messages. Do not run destructive cleanup tests in the real project checkout.

## Out of Scope

- Implementing the feature as part of writing this spec.
- Development branches per task, automatic merges/pushes, background cold execution and new test worktrees.
- Automatically attributing cold regressions to old tasks, reverting old scores or rolling back successful commits.
- Ghost fixing product code, creating replacement implementation tests, weakening tests or acting as a normal repair Worker.
- Stashing/backing up failed work or preserving it for continuation by the next task.
- Full code review, semantic proof of test quality, blanket assertion-count requirements and framework-specific test policies inside the runtime.
- A separate repair acceptance workflow or automatic resumption without Planner's explicit restart.
- Deleting old Git branches/worktrees as migration housekeeping.

## Further Notes

- Here, the user's phrase “automatically merge” means commit on the shared current branch after the gate; no Git merge is performed.
- The additional requirement from spec preparation is mandatory: a TDD case must be declared, actually added or changed, permanently connected to hot, and executed successfully. These are independently checked requirements, not an optional checklist. Ghost can repair wiring for an existing test, but cannot invent a missing test implementation to bypass this contract.
- Local source inspection found generic front insertion and FIFO operations but no dedicated cold cadence implementation. Reuse the existing scheduling seam to provide the agreed independent-cold-task model rather than assuming cadence/hash tracking already exists.
- Current verification runs in both the structured finalizer and outer mechanical audit, and Ghost currently has a different closeout role. Migration must remove obsolete execution paths rather than merely append another test layer.
- The current domain glossary describes Planner-controlled acceptance rollback. The new automatic-success/Planner-replan model supersedes that description for this flow; terminology/documentation updates are part of implementation, not an instruction to automatically revert commits.
- Project/framework integration must explicitly report its discovery and case-result capabilities. If it cannot validate declared case membership, source association and execution, installation/migration must report that gap; falling back to an exit-code-only TDD claim is not acceptance.
- GitHub publication is blocked by missing CLI authentication. Keep this local spec as the publication body and apply `ready-for-agent` when publishing; do not claim that an issue already exists.
