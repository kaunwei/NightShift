# NightShift Planner / Worker / Explore: 24-hour development contract

Status: ready-for-agent

Updated: 2026-10-24. This consolidated contract incorporates the AI Agent Adapter Protocol and on-demand trial specifications. It also records the removal of the worker env-file configuration design: runtime settings belong to the launcher, and agent settings belong to a shared named registry. The normative decisions below take precedence over older implementation notes. Source observations and remaining limits are recorded separately; this document update does not certify implementation or test completion.

## Problem Statement

NightShift is intended to develop continuously for up to 24 hours without a person dispatching each task. A single long-running agent can accumulate stale conversational context and spend premium reasoning on routine implementation. The system needs a durable work queue, a capable persistent Planner, and fresh, economical Worker sessions that can make verifiable progress without losing project knowledge.

## Solution

Explore supplies read-only, evidence-based knowledge of code ownership, callers, public seams, and report freshness. The Planner continuously reads the accepted specification and current Explore reports, creates dependency-aware tickets, dispatches ready work, evaluates evidence, records acceptance, and advances the queue. Each Worker starts a new session, handles one bounded ticket using a configurable low-cost, fast model, verifies it, and leaves durable output. The Planner uses a stronger model for decomposition, ambiguity, integration, and acceptance. The design optimizes accepted progress per total token; it does not assume a particular savings percentage.

## Implementation Decisions

- Explore is the read-only seam-discovery role; it creates compact reports with freshness metadata, verified source pointers, caller topology, coupling, and migration strategy. Reports are reusable only while referenced paths remain unchanged; an explicit Explore request runs a fresh probe.
- Planner, Worker, and Explore are NightShift roles, each tested through its CLI/state contract. Durable state includes the specification, queue/dependencies, Explore reports, task outcomes, per-registration scores, events, and dispatch acknowledgements. Worker conversation history is not a durable dependency.
- Planner remains responsible for ticket quality, dependency ordering, granularity, acceptance, compact score feedback, and deciding whether work can proceed. Worker handles one claimed ticket per fresh invocation.
- Ticket fields are ID, level, optional dependency, target paths, behavior, verification, forbidden shortcuts, and constraints. Uncertain code topology is investigated with a read-only research ticket; unresolved user intent is escalated.
- A project directory has one active development Worker. Separate Worker IDs identify process/state artifacts, not isolated working copies or permission to modify the same files concurrently. Runtime audits enforce scope and task rules and own status/progress records.
- At batch boundaries Planner reads each executing registration's score: 5 → L1, 3–4 → L2, 1–2 → L3. Planner judges quality/evidence; script owns score arithmetic. Five eligible accepts add one up to 5; rejection resets the window; `no_fault` is excluded. Same-task timeout/budget failures lower that registration's score on failures two and three. Audited success clears the failure count. Unchanged retries keep the same task ID. Historical shared score is retained for inspection, not assigned to an agent by inference.
- Runtime enforces callback and execution deadlines; adapters define and enforce their action units and expose defaults through configuration discovery. Preserve task sizing from `base + target_file_count × per_file`; different adapters need not count equivalent actions. Tool-specific event or marker parsing belongs in adapters.
- Each original task ID has at most one private ghost invocation, including retries, failover, and restart. Missing structured commit messages and verification gaps may use it. Ghost may verify and complete results, but cannot edit implementation or commit. Script performs verified Git finalization. Legal no-change outcomes need neither ghost nor commit.
- Completion requires the ticket verification and runtime mechanical audit, followed by Planner acceptance. A successful process exit or commit alone is not acceptance.
- Each new successful mechanical audit starts with `Planner_Review: pending` in the existing execution journal. The existing score-record operation can update the matching task and audit to `accept`, `reject`, or `no_fault`; repeating the same decision is idempotent, conflicting decisions fail, and older records without the field require confirmation. The Planner checks pending audits on resumption and records its decision through that operation.
- Reports are reusable only while referenced source paths remain unchanged. Failed work is retained for inspection while runtime recovery restores the task baseline. Worker tasks execute in the project directory; legacy isolation settings are ignored and existing worktree/preview data is preserved during upgrades.
- Human controls include model choice, manual score correction, pause/steer/reject, and clarification. Planner continues automatically when scope is clear and ready work exists.
- Measure total tokens per accepted task alongside quality and cycle time; include both roles, context loading, retries, review, and verification.

### Collaboration SOP and decision ownership

- **Continuous loop:** check pause and dispatch gates; read status/queue, domain docs, current Explore reports, and the selected registration's score; enqueue the known dependency graph; run/wait for a Worker; inspect audit/evidence; record per-registration Planner feedback at batch boundaries; accept or remediate; repeat while work is ready. Resolve capability-change events before resuming affected dispatch.
- **Planner owns:** spec interpretation, architecture/seams, decomposition/dependencies, registration-appropriate task levels, ambiguity resolution, trial requests, quality/confidence judgment, batch feedback, capability-event review, corrective tickets, acceptance and integration. Planner never dispatches overlapping development into the same project directory.
- **Runtime owns:** queue claim/insertion/locking; pause and polling; versioned adapter callbacks and execution deadlines; quota/timeout failover; stop confirmation and attempt recovery; status/progress/logs; invariant task prompts; script-owned commits; private ghost allowance; mechanical audits; report archives; per-registration score arithmetic and durable events.
- **Worker owns:** one ticket's bounded implementation, research, or trial delivery; declared verification; structured outcomes, evidence, attempts/confidence, and commit message. Worker does not commit, set score, widen scope, change models, edit runtime-owned progress, or use ghost for further implementation.
- **Explore owns:** read-only source topology discovery for the Planner. Reports contain topology/callers, interface skeletons, coupling bottlenecks, source pointers, and migration strategy. Explicit Explore invocation requests a new probe; cache reuse is allowed only when source references remain current.
- **Queue ticket contract:** `TASK-ID | LEVEL | [AFTER: TASK-ID] | TARGET: paths | ACTION: observable change | VERIFY: command | FORBIDDEN_SHORTCUTS: ... | CONSTRAINTS: ...`. `[GUIDANCE]` carries human clarification. New IDs mean changed scope/granularity; unchanged retries keep the original ID.
- **Task type contract:** `[CODE: FIX]` may change product files but not tests. `[CODE: REFACTOR]` may change declared tests, preserves assertion count, and proves structural closure. `[CODE: EXPAND/MIGRATE/CONTRACT]` is phased green-to-green. `[DIAGNOSTIC]` proves a failing repro without changing product code. `[RESEARCH]` leaves product files untouched and emits validated reports. `[BENCHMARK]` reports measured results.
- **Granularity:** L1 at score 5 gives bounded acceptance intent/paths and lets Worker choose internals. L2 at score 3–4 names target files, signatures/error boundaries, and deterministic verification. L3 at score 1–2 gives exact behavior, fixtures, and red/green/verify steps. L2 deletion ceiling is 150 lines; L3 is 40; L1 is target bounded. Multi-interface/refactor gate requires inseparability, one cohesive vertical slice, score-compatible blueprint (L3 below 3), and topology proof.
- **Planner acceptance SOP:** first require mechanical audit PASS, verification exit 0, at least one test for code tasks, whitelist PASS, and clean tree. Then judge requested behavior, evidence quality, test relevance, scope, report pointer validity, and declared confidence. A clean first attempt with HIGH confidence may fast-track integration; retries, MED/LOW confidence, critical seams, audit failure, or `[DEAD_END]` require focused diff and code review. `[DEAD_END]` requires an isolated passing test or runtime evidence that the suspected subsystem is healthy while the symptom remains. Record a compact result and evidence pointer; do not write narrative scoring rationale into script state.
- **Confidence contract:** HIGH = first attempt with zero warnings; MED = one or two retries; LOW = brittle result or unverified edge cases. Worker reports attempt trace and evidence pointers; runtime prepends task status and mechanical audit to progress.
- **Cadence and intervention:** retain the ten-task review and refactor cadence. Normal scoring happens at batch boundaries and belongs to the executing registration. Guidance, decomposition and scope outcomes keep their existing meanings. Capability-change events gate new dispatch until Planner acknowledges or revises affected tickets. Clean Pivot requires authorized recovery scope. Ghost is private internal work under the original task ID, without its own queue entry, score, cadence or watcher handoff.
- **In-place execution and steering:** execution, verification, script-owned commits and recovery use the project directory. Runtime does not create/reuse Worker worktrees or publish previews. Human can Continue, reorder/tweak queue, pause or Reject/replan. Tool-specific access/model/effort belongs to agent config; runtime timeout and pause belong to launch settings. Upgrades preserve old worktrees, branches and previews for manual inspection; unmerged work is not migrated automatically.

### On-demand trial tasks

- Planner represents a trial as an ordinary queue task, with project-specific build and runnable-check commands, output location, required files, and evidence.
- The `queue-insert` CLI inserts the task before pending work under the same queue lock used by claims. It reads the live queue inside the lock, preserves order/comments, and is idempotent by task ID. A running task is already claimed and therefore completes before the inserted task; an idle Worker claims it next.
- Worker builds the version present when the trial task starts. The binary and required standalone files go under `.trials/<TASK-ID>/`; each delivery uses a distinct directory and a copied binary, never a development-output symlink. Build and check before assembling a task-scoped staging directory, check the staged copy, and rename the complete directory into place only after success. On a failed check, remove only that task ID’s incomplete delivery and report the cause; never use an older delivery as fallback. A manifest or `TRIAL.md` records source task/revision, available program version, build and runnable-check evidence, paths, and launch command.
- Trial tasks use ordinary task execution, verification, audit, and outcome handling. Runtime has no trial-specific task type or successful-task publisher. Build/check failure returns the concrete cause for Planner repair; the previous delivery is not substituted. Successful ordinary tasks continue through the queue.
- `.trials/` is ignored by new and upgraded installations so binary-only trial tasks can finish without source changes or meaningless commits.
- The trial task checks required scripts, settings, environment, assets/data, dynamic dependencies, services/databases, devices, and ports using project/platform-appropriate commands. Its handoff classifies each needed resource as included, shared, or unverified and gives evidence, location, use, and conflict. Safe redistributable resources are included; secrets are not copied. Missing evidence is stated explicitly, and the binary is not described as standalone when it still needs shared resources.
- If a required resource can change or be occupied during development, Planner may recommend a pause but the user chooses. The Planner resolves the actual deployed `PAUSE_FILE` (default `<project>/PAUSE`, relative paths rooted at the project, absolute paths preserved) and supplies the concrete creation and `scripts/status.sh` commands. Pause prevents future claims at the next task boundary; an active task continues. Start a conflicting trial only after status shows `PAUSED` with no current task. The trial task never sets/removes the pause flag and does not pause the following queue itself.
- The installed trial demo covers a standalone binary, a script with a bundled resource, a script reading a shared project file, and a custom pause path. It verifies that a trial task does not set the pause flag itself. The pause case demonstrates the user confirmation flow without invoking a live model.

### Configuration without a worker env file

- Runtime defaults belong to the launcher: identity, queue/history/status/log paths, pause and dispatch gates, timeouts, budget coefficients, polling/run-once, ports and registry location. The launch environment can override documented defaults.
- One agent registry maps stable names to opaque adapter executables, optional arguments/environment, a boolean default flag, and adapter-owned config. Default entries run first; JSON order is preserved within both priority groups. All adapters use the same config contract; models, effort and tool permissions belong there.
- The old worker env file is not a configuration source or required installation artifact. Do not source it, recreate its example, or tell operators to edit it. Existing copies survive only for manual migration. Process environment overrides remain supported.
- Helpers do not execute the launcher to load settings. Planner supplies matching explicit environment overrides for custom paths and Worker identity when invoking status/watcher/queue helpers. Resolve pause from the actual launch configuration and launcher defaults. Checking default status paths does not confirm a different configured Worker.
- Updates replace the owned launcher and preserve an existing registry. Operators review/reapply launcher-default edits or use launch overrides. Legacy env data, scores and unintegrated worktree contents must not be discarded during migration.

### External AI execution contract

Runtime owns task lifecycle; adapters own native tool behavior. An unknown adapter must work by registration alone, without provider allowlists, executable-name inference or core log parsing.

| Callback | Responsibility |
|---|---|
| get_config | Validate protocol/config; return initial capability (1–5), normalized settings and limits/polling defaults. |
| start | Accept task/version/attempt, invariant prompt, work directory, output/result locations, settings, limits and environment; promptly return an execution handle. |
| status | Read local state without model/quota queries; report running or a structured terminal outcome and result location. |
| closeout | Start the one private rescue with original registration/context, separate artifacts and remaining limits. |
| cancel | Stop managed execution within a deadline and confirm termination; accepting a cancellation request is insufficient. |

- Exchange versioned JSON with diagnostic stderr separate from control stdout. Reject malformed replies, unsupported versions and missing results. Distinguish complete, closeout-required, quota, action-limit, callback-timeout, execution-timeout, cancellation failure, cancellation and ordinary failure; retain scope/guidance outcomes.
- Script creates one worker prompt per task version. Registration-specific models, limits and permissions travel through config/environment. Failover preserves prompt content; scope changes require Planner revision. Ghost uses a separate shared closeout prompt.
- Callback-response and full-execution deadlines are independent. Runtime enforces both and respects adapter polling intervals. Adapter action units may differ; enforcement and tool-specific parsing belong at that boundary.
- Main-task quota exhaustion or confirmed nonresponse/timeout may select the next registration, at most once per registration per original task. Quota exclusion persists until reset; timeout exclusion is task-scoped. Ordinary failures and step limits do not trigger replacement. Unavailable work remains queued without busy retrying.
- Capture HEAD/index and existing tracked/nonignored untracked content before each attempt. Stop failed execution, archive unique attempt diagnostics/commits/changes, restore and confirm the exact baseline, then gate replacement on Planner review. Unconfirmed stop or recovery blocks replacement.
- Each registration initializes its score through get_config. Built-in Codex and AgY default to 5 in their adapters; runtime cannot infer this from names. Planner quality feedback belongs to the executing registration at batch boundaries. Agent/capability changes produce durable events with cause, affected task and before/after identities/scores. Watcher deduplicates across restart; new dispatch waits for acknowledged/revised resolution. Watcher never launches Planner or rewrites tasks.
- AI returns structured outcome, evidence, change/no-change reason and commit_message. Script verifies and commits. Message presence alone does not authorize success. A justified no-change task, including binary-only trial delivery, follows ordinary verification/audit without meaningless commit or ghost.
- Missing message or unfinished verification may use one ghost allowance per original task ID across retries, failover and restart. Ghost may verify and complete results, cannot edit implementation or commit, remains with its originating registration and cannot trigger replacement. Failure, quota or nonresponse ends rescue without another ghost.
- Ghost and other script-owned internal AI work retain internal diagnostic/cancellation records but create no independent Planner task, DONE entry, watcher handoff, review cadence or score. Planner sees the original task's final outcome and evidence.

### Runtime script capabilities and state contracts

- **Daemon/queue:** claims one task atomically under a queue lock; preserves comments and task ordering; honors `PAUSE`, polling interval, and run-once mode; calculates progress and budget from queue state; restores quota-exhausted work to the front.
- **Adapter execution:** invoke an opaque executable through get_config/start/status/closeout/cancel JSON callbacks. Runtime does not construct provider commands or parse provider logs. Quota exhaustion and confirmed callback/execution timeout may select the next registration after stop confirmation, baseline restoration and Planner gate resolution. Ordinary errors, step-budget exhaustion and ghost failures do not select a replacement.
- **Outcome states:** success proceeds to mechanical audit; timeout/action-budget/closeout failure are hard failures and lower score on same-task attempts 2 and 3; scope and guidance outcomes are reported without score penalty; ordinary CLI/audit errors are blocked failures; quota exhaustion requeues without marking task failed. Status and progress distinguish idle/running/paused, completed, blocked, scope-blocked, awaiting-guidance, and quota-exhausted states.
- **Score CLI/state:** initialize each named registration from adapter get_config (1–5); score-read/score-record with an agent ID read and update that registration under locks. Five accepts raise one level of score, rejection resets the window, no_fault is excluded, and hard-failure rules remain. Score changes and agent switches produce durable events; watcher handoffs are deduplicated and restart-safe. Legacy shared score remains inspectable but is not the planning authority.
- **Git/mechanical audit:** verifies task diff is committed and clean; checks target whitelist; disallows product changes for diagnostic/research; protects tests for FIX; checks assertion non-decrease; enforces L2/L3 deletion limits; runs VERIFY with timeout and port environment; rejects empty test runs; runs full Swift regression when applicable. Research audit checks no product edits, required report artifact/headings, stamps `REPORT_META`, validates source pointers, and runs optional custom verification.
- **Report cache:** `archive-reports` archives active reports before new research; `archive-overlapping-reports` archives reports whose referenced files changed in a code commit. It is path-based invalidation; it does not semantically re-evaluate unreferenced facts.
- **Failure recovery:** `rollback-failed-task` saves tracked diff and untracked files under failed-task storage, restores the task workspace baseline, and retains queue/progress runtime state needed to report or retry.
- **Status/diagnostics:** `status-write` and `status-display` maintain/read machine status; shell helpers watch worker, reorder queue, print status, extract bounded skeletons, and probe source lines. Status and logs are observability interfaces, not score authorities.
- **Configuration contract:** worker runtime defaults live in the launcher and may be overridden by the launching environment. One JSON registry maps stable agent names to default flag, adapter, command, optional args/env and config. Default registrations run first, preserving JSON order within each priority group. Config is passed through the common callback contract for adapter interpretation. No launcher, runtime, helper or Planner workflow may source or require the removed worker env file. Human owns model choice; no proactive model/quota queries.
- **Replaceable agents:** unknown adapter names are supported without core edits or provider-name inference. The selected registration owns command/args/env and adapter config, including model/effort/permissions. A nonempty log is not a structured outcome. Version, field and result validation fail explicitly rather than guessing.
- **Closeout acceptance:** one private ghost per original task ID, including retries, failover and restart. It stays with the original execution registration, uses separate prompt/artifacts and remaining limits, and may supply verification or a missing message. Script checks for implementation edits and performs verified commits. Ghost failure is the original task's final failure; no repeated ghost or agent switch. Legal no-change results finish without ghost/commit.

### On-the-fly development acceptance contract

1. Maintain an accepted spec as the durable product goal. Planner turns it into the complete known dependency graph; each ticket is a vertical, independently verifiable increment. Do not wait for a person between clear tickets.
2. Use Explore before ticketing when target seams/callers are unknown. Do not run duplicate research when a current report already answers the question, unless `/explore` is explicitly requested.
3. Before each batch, use the selected registration's score to set task level. Resolve durable capability-change gates before dispatch. Run ready tickets sequentially in the project directory; queue locks protect claims and insertion/reordering.
4. Worker owns implementation and first-line verification. Runtime independently reruns required verification and audits scope, tests, report artifacts, and repository cleanliness. If runtime audit fails, isolate failed changes, restore the task baseline, record failure, and block or re-slice according to outcome.
5. Planner acceptance is a second funnel: audit PASS is necessary but not sufficient. Planner checks feature intent, credible evidence, test adequacy, task scope, confidence, report freshness, and negative claims. Clean first-pass HIGH can use fast integration; all other risk signals receive focused review and remedial ticketing.
6. Only Planner feedback records accepted quality. Runtime increments/decrements score under the defined cadence; hard runtime evidence bypasses model judgment. Ghost completion and no-fault environment/scope outcomes are excluded from normal acceptance cadence as defined above.
7. Worker tasks use the project directory; the runtime does not publish successful previews. Human can hold or redirect the queue. When ambiguity requires product judgment, preserve the question in task/progress state and wait rather than guessing.

These specifications are the behavior contract for future edits to NightShift-owned skills and scripts. Implementation may change internal modules or helper names while preserving these role contracts, state transitions, failure semantics, audit gates, and handoffs. Changes to those externally observable behaviors require an explicit spec update and corresponding CLI/state regression coverage.

### Source audit baseline

The source audit and coverage index in [NIGHTSHIFT_SOURCE_COVERAGE.md](NIGHTSHIFT_SOURCE_COVERAGE.md) enumerate every NightShift-owned input and runtime function. Preserve both the skill requirements above and the as-built behavior below when simplifying; changes to either require an explicit decision.

### As-built behavior and limits (source audit)

The following records what scripts actually do, including differences from the skill contract. These differences are documentation findings, not implementation changes.

1. Queue claims are FIFO: skip blank/comment lines, remove the first task, and preserve the rest under a directory lock. Dependencies are not evaluated by runtime. One daemon processes one task at a time; Planner arranges dependency order and must not dispatch concurrent development into the same project directory. Claims are removed before execution, not a durable lease with crash replay.
2. Task field parsing recognizes LEVEL, TARGET, ACTION, GOAL, VERIFY, FORBIDDEN_SHORTCUTS, CONSTRAINTS, DEPENDS_ON. Pipes split fields only when followed by one of those names; AFTER/GUIDANCE are not separately parsed fields. LEVEL defaults to 1. Targets are comma-separated; directory targets count contained files recursively, minimum one; missing/empty targets also count at least one for budget.
3. PID files prevent duplicate daemon instances per Worker ID. Dead/malformed PID files may be replaced; permission failure is treated as an active process. SIGINT/SIGTERM request loop shutdown. Status is updated at lifecycle transitions, not continuously while a model is running. Shutdown removes PID and writes STOPPED, except all-quota exhaustion in explicit RUN_ONCE tests writes QUOTA_EXHAUSTED.
4. Pause is checked before claims and holds future work, not a running invocation. RUN_ONCE exits when queue becomes empty, rather than after exactly one task. Normal per-task failure records state then the loop continues to remaining tasks; when no tickets remain it preserves the failure state while waiting for Planner. Action-budget exhaustion emits NEED_DECOMPOSITION for Planner to return a revised bounded ticket. PAUSE holds claims without terminating the daemon. BLOCKED does not stop the daemon.
5. Status JSON contains identity, OS/platform, project work directory, lifecycle/task/elapsed, queue progress, PID, CLI/timeout and UTC heartbeat. Running tasks refresh elapsed time and heartbeat every second; writes are serialized with workspace snapshots and cannot overwrite a later lifecycle transition. Current daemon status uses registered-adapters and retains legacy shared-score/recommended-level fields; these do not replace per-registration score state for planning. Completed counts include failure history, not only accepted work.
6. Runtime sends the same task-version prompt through the common executable protocol. Codex command construction, output parsing, approval/model/effort handling and event counting belong to its adapter, not runtime. AI returns a structured message; script owns commits after verification.
7. AgY and generic wrappers use the same five-callback protocol. Their adapters own native command/API transport, output interpretation and action units. The generic compatibility adapter requires structured JSON results; legacy text-only wrappers need migration.
8. Adapter action units may differ. Runtime supplies task budget/limits independently of invariant prompt content. Adapter-specific parsing and enforcement must be documented and checked at the executable contract rather than duplicated in core.
9. Each callback has a response deadline; full asynchronous work has an independent execution deadline. Runtime kills timed-out callback process groups and requests cancellation of the managed execution. A replacement cannot start unless termination is confirmed. Repeated running status and missing log output do not alter these rules.
10. Runtime validates structured outcomes, runs applicable verification, and finalizes Git using commit_message. Missing message or closeout_required may claim one persisted ghost allowance per original task. Ghost files/prompts remain separate and implementation snapshots are compared before/after. This is final-state auditing, not an OS read-only sandbox. AI commits are forbidden; valid no_change needs a reason and no conflicting source changes. Attempt capture/recovery separately saves HEAD/index/tracked and nonignored untracked baseline content.
11. The canonical registry is a JSON object keyed by stable agent name, with default/adapter/command/args/env/config. Defaults sort first; other relative order is preserved. Invalid entries fail explicitly. Config is normalized to callback overrides internally; this does not create another user-facing registry. Quota state persists, timeout exclusions are task-scoped, ordinary errors do not fail over, and a registration is not retried indefinitely within the original task. All-unavailable work remains queued; explicit run-once may exit. Replacements wait for the durable Planner gate.
12. Each registration initializes its independent 1–5 score from get_config. Score/accept-window/failure history are locked and atomically written; quality feedback names the executing registration. Legacy shared-score CLI/state remains for compatibility/inspection. Capability changes produce event IDs, watcher cursor/ack state and a dispatch gate; acknowledgement does not launch a Planner. Ghost has no independent score entry. Legacy arithmetic still does not deduplicate accepts by task ID; callers must avoid duplicate feedback.
13. Attempt-scoped Git audit compares the captured baseline worktree tree to the current tree, including untracked content, so unchanged pre-existing user edits do not count as task changes. Scope, assertion, deletion and post-commit checks use that same delta. Commits use a temporary index and preserve unrelated user staging; overlapping task changes with baseline dirty worktree or staged paths are refused rather than mixing user work into the commit. Legacy audit calls without an attempt snapshot still compare against the supplied base. It has explicit exemptions: runtime/report paths; test-refactor-approved can authorize test edits; large-deletion-approved or unrestricted bypass deletion limits; unrestricted/multi-interface and diagnostic/research bypass normal target checking. Missing TARGET skips whitelist checks. These exemptions must be retained or deliberately revised.
14. Code VERIFY runs only if supplied. Nonzero exit rejects; known zero-test output patterns reject; Swift projects run a full regression after a successful nonempty VERIFY. There is no universal parsed test count or compiler/linter-warning detector. A PASS journal line prints Tests_Run >=1 even when this was not measured. The skill requires real verification and Planner must check its evidence.
15. Diagnostic audit permits a failing verification except recognized compile/syntax/link failure patterns; it does not prove that the failure is an assertion. Research audit checks dirty state/artifact/headings, adds metadata when absent, and checks only the first five recognized pointers and only their existing-file line upper bounds. Missing referenced files, 5 KB limit, required skeleton attachment, all pointer validity, and proof-of-negative are not fully enforced by script. Existing metadata is not revalidated against HEAD.
16. Research artifact selection uses declared file first, then a SUMMARY under reports, then a research Markdown fallback. Code/research custom VERIFY has 180-second default audit timeout and receives PORT/TEST_PORT. Research REPORT_ONLY/none skips command verification. Audit outputs status/error/verify_exit/messages; CLI returns the JSON report rather than using the guard status as its process exit.
17. Worker tasks use the resolved project root as their working directory regardless of legacy `WORKER_ISOLATION` values. Session startup updates the session-base tag. Worker IDs have separate process/state files but do not provide isolated working copies.
18. New research archives all nonhidden active report entries. Code overlap invalidation uses changed-path substring matches in each active summary; it does not hash every dependency or scan arbitrary source relationships. Diagnostic commits do not trigger overlap invalidation. Archive names include timestamps.
19. Main-attempt recovery captures HEAD/index and original tracked/untracked work, archives failed changes and commits after execution stops, then restores and confirms the baseline before replacement. Missing/unsafe recovery blocks replacement. The standalone legacy rollback path without a baseline only archives unstaged tracked/untracked work and restores worktree files; it does not undo HEAD/index or restore ignored files. It is not sufficient for failover recovery. Runtime state remains current. Runtime verification/audit/finalization errors persist with phase, code and reason in adapter results, the worker log and failure summaries; rollback preserves the current status and log.
20. Queue reorder replaces the complete queue from a file or stdin under the shared queue lock. `queue-insert` inserts one task before pending work while holding that lock, preserves remaining order, and does nothing when its task ID is already queued.
21. Watcher exit codes are 0 empty queue with IDLE/STOPPED, 1 BLOCKED/AWAITING_GUIDANCE, 2 wait timeout, 3 SCOPE_BLOCKED. It searches progress for PASS but does not prove the latest record passed. QUOTA_EXHAUSTED is not a special watcher exit and may wait until timeout. Defaults are one hour/five seconds. Status dashboard shows HEAD and outcome counts, not proof of Planner acceptance.
22. Both source helpers require NIGHTSHIFT_WORKER=1; probe prints numbered context around a requested line, while skeleton uses declaration-pattern matching capped at 40 lines, not a compiler AST. Both support file-plus-line or file#L syntax. Language hints cover Swift/Python/TS/JS/Rust/Go.
23. Installer accepts one existing target, resolves physical paths and no-ops on self-install. It overwrites owned launcher/runtime/helpers/skills/tests, deploys built-in adapters, initializes missing named registry/state, preserves existing registry/queue/history/notes and legacy work data, removes the obsolete env example and named obsolete skills, and validates deployed syntax. Existing worker env data is retained but not read. Local launcher edits are overwritten and need review/reapplication. Target AGENTS/CLAUDE/README are not edited; installation does not run the regression suite.
24. Skills retain requirements not enforced by runtime: Terminal A firewall with intervention exceptions, full-horizon slicing, four refactor gates, Track A/B thresholds, ten-task review, fast/deep acceptance, fast-forward integration, human clarification, compact evidence, confidence meanings, zero warnings/lint, no unsafe shortcuts, bounded notes, and authorized Clean Pivot. A resident Planner agent must execute this SOP; the daemon does not itself read specs, launch a premium Planner, or implement the full dependency graph.
25. Atomic state writes replace sibling temporary files and preserve permissions. Queue, score and event locks have bounded waits. Launcher defaults and its exported environment configure runtime; helpers take their own defaults/launch-environment overrides and do not execute launcher code. Agent config belongs to the shared named registry. Worker IDs namespace process/status/quota files but do not isolate source or turn the historical shared score into the per-agent planning score.

26. End-to-end startup/helpers require Bash/Git and shell tools; process-control branches alone do not establish native Windows deployment. Research product-read-only and ghost no-edit checks are not OS sandboxes. Planner/Explore remain agent skills, not executable schedulers. Some existing skill text still references shared scores or reading the removed worker env file for trial pause resolution; those instructions are stale and must follow the per-registration and launch-configuration contracts above. Source inspection is not proof that all acceptance scenarios have passed.
27. Successful audit records include a pending Planner review field. Review recording identifies the exact task and audit timestamp, updates only that record, and uses the configured progress-log path. Progress prepends and review writes share a bounded lock so concurrent journal updates preserve unrelated history. A repeated identical review does not record score feedback again; a different result against an already reviewed audit is an explicit conflict. An older audit without the field is left unchanged and is not automatically scored.

## Testing Decisions

- Test each NightShift role at its highest stable CLI/state contract. Assert observable dispatch, report freshness/artifacts, persisted state, process outcome, audit, or handoff; avoid private helpers, prompt wording, and chain-of-thought. Planner/Explore CLI/state seams describe role-level verification, not a claim that separate executable schedulers already exist.
- Planner tests cover queue selection/dependencies, score-to-level mapping, feedback, evidence-based acceptance, stop/continue and recovery after a Worker exits.
- Planner review tests exercise the existing score-record CLI and persisted journal/score state: pending-to-reviewed transitions, duplicate and conflicting decisions, independent audits for one task, legacy records, and preservation of unrelated journal entries. Use deterministic local fixtures without model calls.
- Worker tests cover fresh invocation, model/effort, timeout/budget propagation, target/archetype enforcement, verification, progress/commit, hard-failure classification, and restricted closeout attribution.
- Explore tests cover read-only behavior, report metadata and pointer validation, invalidation/archive, bounded report artifacts, and seam-digest output.
- Cross-role tests pass a Planner-created ticket to a fresh Worker, audit its result, expose compact evidence, and select the next eligible ticket without losing dependency or score state.
- Prior art is the standard-library Worker runtime suite covering queue/polling, Codex/AgY CLI, timeout, mechanical/Git audit, reports, rollback, score transitions, and ghost closeout. Use deterministic fake CLIs and repository states; tests must not contact models or consume tokens.
- A good test asserts externally visible behavior through the role's CLI/state interface, not its implementation details.
- Prefer the existing runtime CLI/daemon plus durable-state seam, using temporary installed repositories and deterministic fake adapter executables. Exercise the five-callback protocol at that same executable boundary; no new internal seam is required.
- Cover unknown adapters, shared prompt hashes across failover, config pass-through/default order, callback versus execution deadlines, confirmed cancellation, quota versus task-scoped timeout exclusion, exact baseline recovery and refusal to replace an execution that may still write.
- Cover script-owned commits, missing-message rescue, valid no-change, persisted one-shot ghost across restart/failover, forbidden ghost edits, and absence of independent ghost tasks/scores/handoffs.
- Cover per-registration initialization/arithmetic, batch attribution, durable capability events, watcher deduplication/restart and dispatch held until Planner resolution.
- Cover env-file-free fresh/upgrade startup, registry preservation, retained but unread legacy env data, launcher/environment overrides and helper commands with matching custom paths/Worker identity.
- Cover trial insertion behind active work, separate checked binary deliveries, build/check failure, continued queue execution, bundled/shared/unverified resource evidence and user-controlled pause at a task boundary. Extend the installed trial fixtures; never auto-pause merely because a trial finds conflict.

## Out of Scope

- Automatic model changes, Planner self-scoring, or using model-reported confidence as score arithmetic.
- Recursive ghost rescue, ghost agent switching, or treating ghost as a new Planner ticket.
- Accepting work solely because it was fast, cheap, exited successfully, or committed.
- Promising token savings before comparable work is measured.
- Removing human pause, clarification, model selection, or score correction.
- Requiring a specific vendor, tracker, language, build system, or test framework.
- Restoring worktree isolation, automatic preview publishing, worker env-file configuration, concurrent development into the same project directory, automatic Planner startup, or additional real AI providers.

### Architecture tradeoffs

The architecture trades repeated coordination and context loading for role specialization, fresh Worker sessions, and durable handoffs. It should perform best when tickets are independently verifiable, reports stay current, and Workers succeed quickly; tiny tickets and retries can erase savings. Future skill or script changes should preserve this contract or deliberately revise it.

Matt skills such as to-spec, to-tickets, tdd, and code-review are workflow references for agents using NightShift. They do not define NightShift runtime behavior and are outside this spec implementation scope. The selected NightShift test seams are Planner, Worker, and Explore CLI/state interfaces; cross-role tests cover their durable handoff.
